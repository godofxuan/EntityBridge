2026-09-12。算法结果、来源审计与合成治理验证分别报告。以下数字均来自实际产物；[原始数值与 SHA-256](evidence/SHA256.json) 随源码交付，原始大数据、模型和逐边文件保留在忽略的 `artifacts/`。

## 重新封存的 A 类测试

原始两源共筛得 57,170 个可交叉对应企业。修正缺失国家的 blocking 行为后，旧 v3 测试集已成为开发证据，不能继续称为未见测试。最终数据从全部旧 50,000 个企业之外取剩余 7,170 个企业作新 test；train 59,764 条、validation 20,000 条与 v3 文件逐字节一致。最终全量为 **94,104 条记录**，不是把约 94k 写成 100k。

新 test 为 14,340 条记录、7,170 个正例配对；与旧实体、source key 和 record ID 均零重合。模型只读取八列允许字段，真值只用于 evaluator。训练 TF 固定；阈值在验证集上按 F1、precision、较大阈值的顺序选定，然后写入冻结配置再计算 test 效果。完整性预检会先读取测试 ID/哈希验证隔离，这不是测试效果调参。

| 方法 | 验证集选择阈值 | TP / FP / FN | Precision | Recall | F1 |
|---|---:|---|---:|---:|---:|
| 精确名称 | 1.0 | 7102 / 0 / 68 | 1.0000 | 0.9905 | 0.9952 |
| 模糊名称 | 1.0 | 7102 / 0 / 68 | 1.0000 | 0.9905 | 0.9952 |
| Splink | 0.9999 | 6357 / 0 / 813 | 1.0000 | 0.8866 | 0.9399 |

三者使用同一候选并集，候选召回 **0.998047**。Splink 的 813 个漏配中有 14 个候选遗漏，其余 799 个是评分/阈值遗漏。精确法这两项分别为 14、54。Splink 不优于名称基线；干净当前名称、较高的验证阈值和当前未校准参数限制了其召回。观测到 FP=0 不能解释为上线零风险。

三种方法新 test 均未出现误合并簇；B-cubed precision 均 1，recall 分别 0.9953、0.9953、0.9433。待复核候选数量分别 0、6,746、20,976；这是规则区间计数，没有证明真实人工工作量或节省时间。没有独立人工标签，因此“Splink+约束”在 A 类中的效果与 Splink 一样，未将金标登记号转换为隐藏约束。

## B 类：官方曾用名派生条件

每个条件共 18,596 条记录、9,298 个企业；test 均为 3,804 条记录、1,902 个企业。使用真实官方曾用名替换 GLEIF 名称，CH 仍为当前名称。下列是分开的受控条件；当前地址是复制值，不能当作实际历史地址。

| 查询条件 | 候选 recall | 模糊名 P / R / F1 | Splink P / R / F1 |
|---|---:|---|---|
| 只有曾用名 | 0.1951 | 0.7107 / 0.1951 / 0.3061 | 无接纳配对；R=0、F1=0 |
| 曾用名＋当前邮编 | 0.2981 | 0.7527 / 0.2944 / 0.4233 | 0.9241 / 0.2177 / 0.3523 |
| 曾用名＋复制当前地址 | 0.8607 | 0.7524 / 0.6472 / 0.6959 | 0.6911 / 0.8433 / 0.7596 |

精确法三组均仅 TP=1、FP=1，F1=0.0011。只有名称时，当前 Splink 配置在给定验证阈值网格中未选出有效接纳，最终阈值为 1；报告中 precision=0 是空预测集合的计算约定，不能解释为“接纳结果全部错误”。训练 manifest 保留未观察层及默认参数信息。

复制地址条件下 Splink F1 较模糊名提高，但 precision 降低，误合并簇从 135 增至 148，误簇记录从 647 增至 740，最大误簇均为 17 条记录。这里的提高不是无代价的整体改善。仅邮编时 Splink 提高 precision、降低 recall/F1。名称完全变化而地址缺失的候选覆盖仍是主要未解决问题。

## 规模与性能

单机 Windows 11、Python 3.12.13、12 逻辑核、33.95 GB RAM。时间是单次实测，不是延迟分位数或生产 SLA。并发运行过部分独立验收，下面只作复现参考。

| 实验 | 实际记录 | 全量候选 | 实验总耗时 | 进程峰值内存 |
|---|---:|---:|---:|---:|
| 初期 10k（旧 blocking） | 10,000 | 11,309 | 35.76 s | 见原 JSON |
| 开发期 v3 100k | 100,000 | 914,580 | 51.45 s | 4.22 GB |
| 最终封存发布集 | 94,104 | 846,212 | 46.46 s | 3.96 GB |

实验总时间包含训练、验证、test 和全量候选/评分/归并，不包含数据下载和数据库接入。各阶段时间见报告 `seconds`。旧 10k 存在逐边重复计算模型指纹的性能缺陷，不能拿它和修复后的版本直接声称增量加速。

另一次真实 10k PostgreSQL 整合验收，两源各 5,000 条，严格去除 evaluator 字段后经 API 导入并执行冻结 Splink。导入 7.992 s、匹配与候选版本 2.823 s、发布 0.434 s、全部企业查询 0.402 s、固定版本 CSV 导出 0.252 s，总计 13.274 s。13,033 对候选；版本文件 25,808,479 字节、CSV 10,000 行。7 项完整性断言通过，临时测试 schema 已清理。使用 ASGI TestClient，实际执行 PostgreSQL 与模型，属于整合验收而非网络压测或效果评估。[整合运行报告](evidence/real_workflow_10k.json)

独立复验在修复后的旧 100k 上实际返回 **914,580** 条预测：候选 5.935 s、评分 18.385 s、峰值约 3.842 GB。DuckDB EXPLAIN 为 4 个 HASH_JOIN，没有 CROSS_PRODUCT 或 BLOCKWISE_NL_JOIN；在同一 100k 输入中请求一对，实际预测也只有一对。详细过程见[独立审查](INDEPENDENT_REVIEW.md)。

## C 类：真实记录上的合成变更与治理

10k 真实记录保留固定模型和 TF，分别合成一次更名、删除、插入。变更记录明确标记为合成回放，不进入 A/B 效果统计。更名和插入各实际重评 1 对，删除重评 0 对；均与全量每一对分数在 1e-12 内一致，最终分区相同。

| 变更 | 受影响记录 | 增量 / 全量时间 | 实际重评配对 |
|---|---:|---|---:|
| 更名 | 2 | 0.367 / 1.118 s | 1 |
| 删除 | 2 | 0.069 / 1.156 s | 0 |
| 插入 | 3 | 0.295 / 1.225 s | 1 |

这是三个具体场景，不能泛化为统一加速倍数。实现仍扫描当前记录找桶、读取版本文件；只保证固定策略下局部重评分/解析与全量等价，复杂闭包超过预算会以同策略全量兜底。[逐项回放证据](evidence/incremental_10k_v2.json)

独立 Boolean Floyd–Warshall 参考实现覆盖 200 组完整图、250 组变化图，比较分区和逐边状态/理由/冲突；另有 150 组生产全量对照。SQLite 与 PostgreSQL 均通过真实子进程在文件落盘后被终止的恢复验收；当前发布指针不暴露半成品，重跑可发布，旧版本仍可查询。[SQLite](evidence/failure_recovery_sqlite.json) · [PostgreSQL](evidence/failure_recovery_postgres.json)

## 完整性与限制

- 最终完整测试 69 项通过（含 PostgreSQL 迁移/恢复）；PostgreSQL Store 的 7 项测试另行运行通过。干净虚拟环境常规 67 项通过、2 项 PG opt-in 明确跳过，另实测演示三页及 health 全为 200。
- `baseline_10k_v1` 在 pandas NaN 处理上失败，未产生 test 报告；`baseline_100k_v1` 因指纹重复计算过慢中断。最终首次尝试 `release_final_v1` 因旧模型缺训练来源哈希被预检拒绝，尚未评 test；`release_final_v2` 从允许的同一 train 重新拟合并完成唯一一次新 test 效果计算。所有失败记录保留，没有删除后只展示成功。
- 数据是有登记号且可交叉对应的闭集，两源可能共享登记来源，跨快照相差 11 天；不是全体无编号企业、跨国业务或采购订单。新 test 是同一快照企业补集，不是时间外推。
- 模型概率未校准；Wilson 区间是配对计数的描述性区间，不保证样本独立。没有真实双人标注、人工预算收益、避免采购损失或线上稳定性指标。
- 发布服务使用不可变 JSON 产物与关系表，当前查询读取完整版本；约 100k 匹配计算与真实 10k 数据库验收是不同测量，不能混称 100k 线上吞吐。
