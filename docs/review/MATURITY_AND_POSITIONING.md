# EntityBridge 的价值、架构和成熟度

核验日期：2026-09-12。本文件区分代码中已经存在的能力、实测证据和仍需验证的目标。比较只引用各项目的官方文档，没有在同一基准上运行其他产品，不构成性能排名。

## 项目实际解决什么

两个系统可能把同一家公司分别记为“Northstar Energy Limited”和“Northstar Energy Ltd”；相反，同一个地址上的两家公司可能是不同法人。EntityBridge 将来源记录关联到统一企业身份，同时保留“为什么合并、谁确认过、后来为什么拆开”的依据。

它覆盖来源导入、版本记录、候选生成、评分、约束归并、人工复核、撤销、版本发布和历史查询。可信登记号匹配与缺失标识的文本匹配使用分开的入口；分支机构和继承关系不会直接被当成同一法人。示例界面使用合成公司演示治理，真实匹配效果来自 GLEIF 与 Companies House 实验。[实现入口](../../README.md) · [来源契约](../data/SOURCES_AND_CONTRACT.md)

实用价值在于给跨系统企业数据增加可检查的身份层：例如供应商主数据整理、CRM 与合同数据关联、企业目录对齐。项目并未接入真实采购或 CRM 业务，因此这些是适用场景，不是已经取得的客户成果。减少重复档案和方便追责是设计目标；节省多少人时、避免多少损失需要真实使用实验。

项目中值得展示的工程工作包括：

- 用登记号构建独立评估真值，但在匹配器输入中剥离登记号、LEI、URL 和嵌入文本的标识；按实体切分并校验输入哈希，减少评估泄漏。
- 将模型评分与确定性约束决策分开，人工“不同企业”约束作用于整个簇，不能经第三条记录绕过。
- 以来源版本、决策事件、身份版本和发布指针分别记录事实、判断、结果与当前可见状态；撤销保留旧版本和全部身份去向。
- 固定模型和 TF 后，在旧、新候选及约束支持图的受影响闭包内重算；无法保持局部边界时按相同策略全量兜底，并通过独立参考实现和全量对照验证。

这些是围绕第三方算法实现的数据工程和治理能力。Splink 的 Fellegi–Sunter/EM、DuckDB 的查询执行、SQLAlchemy 的事务设施属于所采用的依赖，不能表述为自研算法。

## 与成熟方案比较：先区分层次

| 方案 | 官方定位与已有能力 | 与 EntityBridge 的关系及差距 |
|---|---|---|
| Splink | 概率实体关联库；提供 TF 调整、训练/评估/可视化，以及 DuckDB、Spark、Athena 等后端。[官方说明](https://moj-analytical-services.github.io/splink/) | 本项目直接使用 Splink。新增的是应用数据契约、约束与身份治理流程，不能把它当作被本项目击败的算法竞品。当前仅集成 DuckDB，未验证分布式执行。 |
| Dedupe | 面向结构化数据的实体关联库，根据人工标签学习字段权重与 blocking；其主动学习优先请求有信息量的标签。[库文档](https://docs.dedupe.io/en/latest/) · [主动学习原理](https://docs.dedupe.io/en/latest/how-it-works/Matching-records.html) | 本项目已有人工复核，但复核是治理约束，未形成主动学习闭环，也未测量每次人工判断的质量收益。Dedupe.io 托管服务与开源库应分别比较。 |
| Zingg Enterprise | 官方增量流程明确涵盖新增/更新记录、持久 ID、归并/拆分与保护已有人工确认；文档将其标为 Enterprise 功能。[官方增量说明](https://docs.zingg.ai/latest/stepbystep/runincremental) | 最接近本项目的持续身份治理目标。说明稳定身份、增量、人工保护并非项目独创；EntityBridge 的可读实现和回归证据适合作品展示，但不能据此声称已具备同等产品成熟度。此比较没有将 Enterprise 能力归给其开源版。 |
| OpenRefine | 交互式数据清洗工具；字符串 clustering 处理书写变体，reconciliation 通过外部服务候选与人工判断关联身份。[clustering 说明](https://openrefine.org/docs/technical-reference/clustering-in-depth) · [reconciliation 说明](https://openrefine.org/docs/manual/reconciling) | 可比较清洗和人工审查体验；不宜把它当作完全同型的事务身份服务。本项目 UI、批量审查、数据探索和导入交互仍较简单。 |

Splink 官方还指出：它更适合拥有多个信息字段的记录，并非专为只有一列公司名的词袋匹配设计。项目曾用名且缺地址的失败，与信息不足及 blocking 覆盖有关；更换算法不能保证凭空补出身份信息。[Splink 适用数据说明](https://moj-analytical-services.github.io/splink/)

## 架构判断

整体分层合理：不可变来源版本是事实；评分和人工决策是证据；resolver 产生身份分区；完整身份版本构建后，事务只切换当前指针。这个结构有助于重现历史和处理错误合并。实体归并的传递性必须由簇级约束控制，这比只对单条边应用阈值更符合纠错需求。[身份决策](../decisions/004-identity.md) · [撤销决策](../decisions/005-revocation.md)

同时，当前是单机作品，不是完整 MDM 平台。`store.py` 集中了导入、约束、产物构建和发布逻辑，后续变化应围绕稳定接口拆分构建器、事件存储与查询服务，而不是让路由重新实现业务规则。目录 API 已支持默认 100、最多 1,000 条的 limit/offset 分页，返回总数和版本头；网页目录与复核队列支持固定版本翻页和复核状态筛选。但后端仍读取、扫描完整版本文件，分页限制的是响应体与页面大小，并未减少底层 I/O；局部重评分也仍扫描记录找桶，不能声称端到端 I/O 次线性。[增量边界](../decisions/006-incremental.md)

人工判断绑定来源版本能防止把旧结论静默应用到变更记录，但会产生需要再次确认的判断；这是明确策略而非自动正确答案。撤销一条边也不必然拆簇，因为可能仍有其他合法支持路径。显示完整影响预览和依据版本是必要产品行为。

## 已有证据与主要差距

| 方面 | 现有证据 | 尚缺内容与可验收的下一步 |
|---|---|---|
| 关联效果 | 未见企业 test 上精确名 F1 0.9952、当前 Splink F1 0.9399；公开保留失败及无增益结果 | 当前名称大多一致，来源可能同源；需要时间外、独立来源、同名异企与真正无登记号样本。先预注册数据和指标，再评价增强，不继续在已看过 test 上挑最好结果。 |
| 候选覆盖 | 当前名称 test 候选 recall 0.998047；仅曾用名条件固定规则为 0.1951，可选冻结字符 n-gram 检索达到 0.4606 | 后者复用已看过的探索性 test，且自动模糊匹配 F1 下降，不能称质量提升。新增 top-k 每次全量生成候选；需要独立标注和 prospective holdout 验证复核价值。 |
| 模型质量 | 固定训练 TF、保存训练来源摘要、字段级证据 | 概率尚未校准；需独立标注与校准集、precision/recall/coverage 和人工预算曲线。不能把高分直接当成可承诺的正确率。 |
| 治理正确性 | cannot-link 传递冲突、撤销、旧 ID 去向、来源变更、并发发布、崩溃边界及独立图参考测试 | 更多重复操作、长历史链与复杂并发组合仍需验证；测试通过不等于不存在 bug。业务对重命名、注销和继承的政策要另行定义。 |
| 性能与运维 | 94,104 条最终离线实验；实际 10k PostgreSQL 整合验收；三个合成变更回放；API/网页响应分页 | 未有线上压测、长时间稳定性、备份恢复演练和容量上限。分页后仍有全版本 JSON 读取与扫描；同步长任务、持久候选索引和数据库索引查询仍是扩展重点。 |
| 产品和安全 | 本地三页界面、viewer/reviewer/admin 三角色、来源追溯、过期操作冲突 | 当前为 loopback、单工作空间 token 权限，未提供企业 SSO、多租户隔离、审批分工、审计保留/删除政策、生产级监控。没有这些证据，不应向互联网开放真实业务数据。 |
| 可维护交付 | 锁定依赖、合成测试、迁移、实际 wheel 资源检查；新增 Windows/Linux CI 定义与公开导出边界 | CI 定义不等于远程执行已通过；以 GitHub 实际运行结果为准。官方数据快照可能轮换；保留数值与哈希不等于仓库包含全部原始数据。 |

上述数字及范围以[实测结果](../evaluation/RESULTS.md)为准；并未横向测量这些成熟方案的准确率或吞吐。

新增 hybrid 曾用名检索将候选召回从 19.51% 提高到 46.06%，候选对从 539 增至 18,481；模糊匹配 F1 反而从 30.61% 降至 19.62%，最大误簇从 9 条增至 241 条。Splink 在两种候选策略下都没有自动接纳配对。该组件仅作为可选复核候选探索，未替换默认匹配策略，也未证明节省人工时间。服务 hybrid 模式显式禁止评分边自动归并，保留分数并交由人工确认。[匹配审查](MATCHING_AUDIT.md) · [数值与配置证据](../evaluation/evidence/hybrid_name_v2_summary.json)

本次公开交付增加 `scripts/check_publication.py`：只导出代码、依赖、选定文档与测量证据，排除内部规划、状态记录、原始数据、数据库、凭据、测试日志和旧 Git 历史。导出保留代码逐字节摘要，重新生成实际公开证据的哈希表；Markdown 中未导出的本地材料链接转为说明。严格导出是避免无意公开本机内容的边界，不是完整安全审计，也不自动赋予开源许可。

## 适合怎样使用这件作品

这是可以展示的个人工程项目；其价值取决于作者能否解释设计取舍、复现结果和现场修改代码，不能仅凭仓库规模判断胜任力。

| 岗位方向 | 有说服力的内容 | 需要补充的能力证据 |
|---|---|---|
| 数据工程、数据质量、主数据治理 | 双源契约、批量处理、实体对齐、泄漏控制、数据版本与追溯 | 具体岗位要求的数仓/调度/分布式生态，以及业务数据质量落地经验 |
| Python 后端、数据平台后端 | FastAPI、SQLAlchemy/PostgreSQL、迁移、并发发布、失败恢复与历史查询 | 网络服务压测、监控、部署、权限体系和团队工程经验 |
| 应用机器学习、匹配/搜索质量评估 | baseline、固定 TF、防泄漏评估、错误分解、候选覆盖与性能分析 | 独立标注、校准、模型改进的可靠增益；目前不能作为算法领先成果 |
| 通用 AI/LLM、Java 后端 | 可作为数据治理补充项目 | 本项目不提供 LLM/RAG、Java/JVM、训练基础模型的经历，不能替代岗位核心技术要求 |

可核验的项目描述示例：

> 构建企业实体关联与身份治理服务，接入 GLEIF/Companies House，分离可信标识匹配与八列无标识评估；实现来源版本、簇级人工约束、撤销预览、历史身份去向和事务发布。
>
> 在 94,104 条真实来源记录的固定实验中比较精确名、模糊名与 Splink，公开记录基线更优及曾用名场景的候选瓶颈；通过独立图参考、全量对照及 PostgreSQL 失败恢复验证治理边界。

不得写成“自研 Splink/EM 算法”“达到工业级零误配”“解决百万级线上并发”“已节约采购成本”“显著提升标注效率”或“全面超越成熟 MDM”。也不应省略合成演示、闭集样本、同源风险和尚未选择项目许可证的事实。
