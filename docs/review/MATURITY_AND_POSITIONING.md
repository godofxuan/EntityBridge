# EntityBridge 的价值、架构和成熟度

核验日期：2026-09-12，更新至 v0.4 实际进展。本文件区分代码中已经存在的能力、实测证据和仍需验证的目标。比较只引用各项目的官方文档；新增公开基准是在本项目内比较评分器，没有在同一基准上运行其他产品，不构成产品性能排名。

## 项目实际解决什么

两个系统可能把同一家公司分别记为“Northstar Energy Limited”和“Northstar Energy Ltd”；相反，同一个地址上的两家公司可能是不同法人。EntityBridge 将来源记录关联到统一企业身份，同时保留“为什么合并、谁确认过、后来为什么拆开”的依据。

它覆盖来源导入、版本记录、候选生成、评分、约束归并、人工复核、撤销、版本发布和历史查询。可信登记号匹配与缺失标识的文本匹配使用分开的入口；分支机构和继承关系不会直接被当成同一法人。示例界面使用合成公司演示治理，公司领域效果来自 GLEIF 与 Companies House 实验；新接入的餐馆、论文公开基准提供跨领域诊断。[实现入口](../../README.md) · [来源契约](../data/SOURCES_AND_CONTRACT.md) · [公开基准契约](../data/PUBLIC_BENCHMARKS.md)

实用价值在于给跨系统企业数据增加可检查的身份层：例如供应商主数据整理、CRM 与合同数据关联、企业目录对齐。项目并未接入真实采购或 CRM 业务，因此这些是适用场景，不是已经取得的客户成果。减少重复档案和方便追责是设计目标；节省多少人时、避免多少损失需要真实使用实验。

项目中值得展示的工程工作包括：

- 用登记号构建独立评估真值，但在匹配器输入中剥离登记号、LEI、URL 和嵌入文本的标识；按实体切分并校验输入哈希，减少评估泄漏。
- 将模型评分与确定性约束决策分开，人工“不同企业”约束作用于整个簇，不能经第三条记录绕过。
- 以来源版本、决策事件、身份版本和发布指针分别记录事实、判断、结果与当前可见状态；撤销保留旧版本和全部身份去向。
- 固定模型和 TF 后，在旧、新候选及约束支持图的受影响闭包内重算；无法保持局部边界时按相同策略全量兜底，并通过独立参考实现和全量对照验证。
- 对公开部分标注数据区分未知配对与明确负例，按已知实体重新划分，分别评测召回和给定配对分类，并报告代价、复核预算、概率诊断和分组置信区间。
- 将目录与实体详情从重复读取完整 JSON 改为可重建关系查询投影，保持固定版本和发布校验，并用相同输入的新旧查询结果及计时进行差分验证。

这些是围绕第三方算法实现的数据工程和治理能力。Splink 的 Fellegi–Sunter/EM、DuckDB 的查询执行、SQLAlchemy 的事务设施属于所采用的依赖，不能表述为自研算法。

|---|---|---|

| Zingg Enterprise | 官方增量流程明确涵盖新增/更新记录、持久 ID、归并/拆分与保护已有人工确认；文档将其标为 Enterprise 功能。[官方增量说明](https://docs.zingg.ai/latest/stepbystep/runincremental) | 最接近本项目的持续身份治理目标。说明稳定身份、增量、人工保护并非项目独创；EntityBridge 的可读实现和回归证据适合作品展示，但不能据此声称已具备同等产品成熟度。此比较没有将 Enterprise 能力归给其开源版。 |
| OpenRefine | 交互式数据清洗工具；字符串 clustering 处理书写变体，reconciliation 通过外部服务候选与人工判断关联身份。[clustering 说明](https://openrefine.org/docs/technical-reference/clustering-in-depth) · [reconciliation 说明](https://openrefine.org/docs/manual/reconciling) | 可比较清洗和人工审查体验；不宜把它当作完全同型的事务身份服务。本项目 UI、批量审查、数据探索和导入交互仍较简单。 |

Splink 官方还指出：它更适合拥有多个信息字段的记录，并非专为只有一列公司名的词袋匹配设计。项目曾用名且缺地址的失败，与信息不足及 blocking 覆盖有关；更换算法不能保证凭空补出身份信息。[Splink 适用数据说明](https://moj-analytical-services.github.io/splink/)

## 架构判断

整体分层合理：不可变来源版本是事实；评分和人工决策是证据；resolver 产生身份分区；完整身份版本构建后，事务只切换当前指针。这个结构有助于重现历史和处理错误合并。实体归并的传递性必须由簇级约束控制，这比只对单条边应用阈值更符合纠错需求。[身份决策](../decisions/004-identity.md) · [撤销决策](../decisions/005-revocation.md)

同时，当前是单机作品，不是完整 MDM 平台。`store.py` 仍集中导入、约束、产物构建和发布编排；查询投影已拆至 `query_projection.py`，后续变化应继续围绕稳定接口拆分构建器和事件存储，避免路由重新实现业务规则。

v0.3 已改善目录查询路径：目录 API 的 limit/offset、总数与结果固定到同一已发布 revision，实体详情通过成员版本连接来源记录；稳定请求读取关系投影，不再每次读取和重新哈希完整 JSON。投影与新候选在同一事务中写入，发布前与原产物验证；旧版本首次访问会校验并回填，损坏可以显式核验、重建。原 JSON 仍是冻结的审计与恢复依据。[查询投影 ADR 008](../decisions/008-query-projection.md)

这一改进有明确边界：名称搜索保持 casefold 后字面子串语义，仍扫描所选版本的精简搜索值，B-tree 不能把任意 `%term%` 查询变成对数复杂度。复核和固定版本导出仍读取完整产物；深 OFFSET、长历史 lineage 与首次回填仍有成本。固定策略局部重评分也仍扫描记录找桶，不能声称所有路径端到端 I/O 次线性。[增量边界](../decisions/006-incremental.md)

人工判断绑定来源版本能防止把旧结论静默应用到变更记录，但会产生需要再次确认的判断；这是明确策略而非自动正确答案。撤销一条边也不必然拆簇，因为可能仍有其他合法支持路径。显示完整影响预览和依据版本是必要产品行为。

公司实验数字及范围以[原实测结果](../evaluation/RESULTS.md)为准；新增内容见[公开基准结果](../evaluation/PUBLIC_BENCHMARK_RESULTS.md)、[评测协议](../evaluation/EVALUATION_PROTOCOL.md)和[查询性能测量](../decisions/008-query-projection.md)。没有横向测量这些成熟产品的准确率或吞吐。

公开基准新增内容解决了“只看单一登记闭集”和“指标口径不足”的一部分问题：原随机配对划分存在记录重叠，现在按已知正标签连通分量划分，并丢弃跨集合负例、保留统计；缺失配对保持 unknown，不补成负例或完整聚类真值。给定标注配对轨道衡量分类能力，不能代替候选召回。阈值只从验证集选择，误配/漏配成本属于实验设定，分组 bootstrap 报告依赖结构，复核预算曲线不冒充人工效率实验。

当前两个公开基准均以 v2 的 `exploratory-replayed` 结果为准。v1 暴露精确名阈值可降至 0、改变“精确相等”方法语义的问题，修复后重放同一数据。保留这个过程比把重放包装成未见测试更可信。Fodors–Zagats 测试仅 55 个明确标签、其中 20 个正例；某个结果满分不能推广到餐馆总体，更不能推广到企业身份。DBLP–ACM 只用标题，且实体划分不同于原论文；结果适合作为可复现诊断，不是榜单成绩。运行命令要求明确提供 `--test-status`。

查询投影则解决了一个可测量的工程瓶颈：在同一个 10k 合成版本、相同分页参数、交替执行的 25 对查询中，SQLite 第一页 p50 从 64.07 ms 降至 2.09 ms，投影稳定查询完整 JSON 读取为零。旧版本第一次回填单独计量约 495.42 ms；包含名称搜索仍慢于空查询。这些是本机预热条件下的应用查询结果，不是生产 SLA，也没有据此推断 PostgreSQL 获得相同倍数收益。投影增加数据库空间和准备/发布成本，需要与查询收益一并解释。

新增 hybrid 曾用名检索将候选召回从 19.51% 提高到 46.06%，候选对从 539 增至 18,481；模糊匹配 F1 反而从 30.61% 降至 19.62%，最大误簇从 9 条增至 241 条。Splink 在两种候选策略下都没有自动接纳配对。该组件仅作为可选复核候选探索，未替换默认匹配策略，也未证明节省人工时间。服务 hybrid 模式显式禁止评分边自动归并，保留分数并交由人工确认。[匹配审查](MATCHING_AUDIT.md) · [数值与配置证据](../evaluation/evidence/hybrid_name_v2_summary.json)

本次公开交付增加 `scripts/check_publication.py`：只导出代码、依赖、选定文档与测量证据，排除内部规划、状态记录、原始数据、数据库、凭据、测试日志和旧 Git 历史。导出保留代码逐字节摘要，重新生成实际公开证据的哈希表；Markdown 中未导出的本地材料链接转为说明。严格导出是避免无意公开本机内容的边界，不是完整安全审计，也不自动赋予开源许可。

## v0.4 补齐的证据和仍未闭合的问题

持久任务、有效复核标签学习、备份恢复、实际HTTP固定负载、JWT身份验证与独立工作区均已实现并有对应测试。详细交付以 [v0.4 验证记录](../evaluation/V04_VALIDATION.md) 为准；不是把所有成熟产品能力一次实现，也不是仅凭测试就宣称无 bug。

[WDC 外部诊断](../evaluation/WDC_UNSEEN_RESULTS.md) 在未见商品实体上暴露明显失败：完整商品字段模型 F1 0.0578、召回率3%，预声明成本525高于标题模型492。验证集重叠修正、模型/阈值冻结和失败结果均保留。应先按业务代价选择评估协议，再研究更合适的表示；不能依据当前测试不断调参后声称获得新的泛化证据。

[主动采样模拟](../decisions/010-review-learning.md) 覆盖三种种子与20/50/100/200标签预算，所有检查点F1相同。它验证了流程和数据边界，没有证明人工效率提升。后续需新时间快照、独立业务标注、真人任务耗时与质量双指标；这些依赖外部真实证据，不能由更多合成样本补成业务成绩。

## 适合怎样使用这件作品

这是可以展示的个人工程项目；其价值取决于作者能否解释设计取舍、复现结果和现场修改代码，不能仅凭仓库规模判断胜任力。

| 岗位方向 | 有说服力的内容 | 需要补充的能力证据 |
|---|---|---|
| 数据工程、数据质量、主数据治理 | 双源契约、批量处理、实体对齐、泄漏控制、数据版本与追溯 | 具体岗位要求的数仓/调度/分布式生态，以及业务数据质量落地经验 |
| Python 后端、数据平台后端 | FastAPI、SQLAlchemy/PostgreSQL、迁移、并发发布、失败恢复、历史查询与可重建查询投影；同输入性能差分 | 固定负载实测之外的容量/稳定性、集中监控、真实部署和团队工程经验 |
| 应用机器学习、匹配/搜索质量评估 | baseline、固定 TF、防泄漏、部分标签协议、候选/分类分轨、成本与校准诊断、独立训练的监督基线 | 业务独立标注、部署校准、模型改进的可靠泛化增益；目前不能作为算法领先成果 |
| 通用 AI/LLM、Java 后端 | 可作为数据治理补充项目 | 本项目不提供 LLM/RAG、Java/JVM、训练基础模型的经历，不能替代岗位核心技术要求 |

可核验的项目描述示例：

> 构建企业实体关联与身份治理服务，接入 GLEIF/Companies House，分离可信标识匹配与八列无标识评估；实现来源版本、簇级人工约束、撤销预览、历史身份去向和事务发布。
>
> 在 94,104 条真实来源记录的固定实验中比较精确名、模糊名与 Splink，公开记录基线更优及曾用名场景的候选瓶颈；通过独立图参考、全量对照及 PostgreSQL 失败恢复验证治理边界。

不得写成“自研 Splink/EM 算法”“达到工业级零误配”“解决百万级线上并发”“已节约采购成本”“显著提升标注效率”或“全面超越成熟 MDM”。也不应省略合成演示、闭集样本、同源风险和尚未选择项目许可证的事实。
