# 007：系统边界与后续选择

EntityBridge 面向企业身份合并后的可解释纠错：同一企业会有多份来源记录，业务判断会变化，统一 ID 的合并与拆分不能抹掉旧证据。因此核心产物是匹配证据、人工决策、版本化身份与发布边界，而非另一个检索问答应用。

第三方 Splink 提供概率评分，DuckDB 执行候选/特征计算，PostgreSQL 保存业务状态。项目自行实现来源适配与隔离、规则候选并集、确定性约束解析、身份 lineage、撤销范围、事务发布、增量闭包和评测流程。人工判断没有被用于自动训练；AI 辅助开发不应包装成独立人工标注实验。

默认不引入 LLM、消息队列或自动训练。公开名称数据的错误主要在候选召回、同名碰撞与关系语义；先验证这些边界更直接。分支/继承是带证据的来源关系，单独保留在记录 payload 和详情页面，不能由关系本身推出 same_as。显式 identifier-rich 入口排除分支/继承及重复编号歧义；无标识名称入口仅接收八列投影。

当前单机实现会读取完整版本 JSON，并扫描记录以找到变动桶。它验证局部重评分/解析的等价性，不宣称整个 I/O 为次线性。候选大桶超过上限会明确失败；大规模生产系统需要分页索引、持久桶索引与后台任务管理。API 仅监听本机，令牌支持 admin/reviewer；没有多租户、互联网 SSO 或生产运维承诺。

后续优先实验字符 n-gram 混合召回，以解决官方曾用名场景的候选遗漏。引入全局 top-k 索引后先全量重建，不能沿用当前局部等价承诺。此增强不属于本次实现，也没有捏造精度或人工效率收益。
