# ADR 005：撤销支持关系与明确判定不同的区别

状态：按当前源码实现。记录日期：2026-09-12。

撤销的含义是让某次判断失去支持效力。若 A–B 的支持被撤销，但仍存在 A–C–B 路径，三条记录可能仍属于同一身份。因此撤销不能承诺拆簇；明确“不是同一企业”需要单独的 reject／cannot-link。

当前 API 支持 accept、reject、abstain。`Store._constraints` 将有效 accept 转为 must-link，将 reject 转为 cannot-link；abstain 和被撤销判断生成自动接受抑制。resolver 首先检查 must-link 的传递闭包与 cannot-link 是否矛盾，然后逐边检查簇级冲突。contradiction 不会以先后顺序静默覆盖，而是在写入新判断前失败。

判断主体存于 `review_decision`，状态变化采用追加 `decision_event`，当前实际事件为 CREATE、REVOKE、EXPIRE。撤销不会删除原判断或过去版本。每个发布产物冻结事件截止序号和当时的有效约束，历史读取使用该产物，不用当前判断状态重写过去。

撤销预览携带 base_revision，返回实际重算分区、前后实体数及 event_cutoff。正式撤销必须提交界面确认的 preview_cutoff；在事务中再次检查当前版本、源记录依据和事件序号，变化时返回冲突。复核还要求两个端点的记录版本和评分策略一致。当前实现会因任意源记录变化使旧复核依据过期，属于保守策略。

抑制只阻止相同端点依据的自动边，不是永久 cannot-link，也不取消其他合法的 must-link。模型重跑时仍读取抑制；策略变化后，REVOKE 与 abstain 的抑制不自动继承到新策略。有效 accept/reject 在端点记录版本未变时可跨模型策略保留。源记录修改会追加 EXPIRE 事件，新版本需重新复核；没有暗中将旧判断迁移到新事实。

源版本和已有判断均正确时，撤销后重新计算完整候选分区，再生成新的身份 UUID 和 lineage。旧版本继续保留合并前后的成员；拆分后的旧 ID 查询返回全部当前去向。计算完成与正式发布分别执行，过时候选不能覆盖新的发布版本。

验收包括三种互补证据：

- `tests/test_resolution.py` 检查间接路径不能绕过 cannot-link、must/cannot 矛盾必须失败以及同边抑制。
- `tests/test_store.py` 运行判断→发布→预览→撤销→发布→历史查询，验证重新运行同一模型不会立即重新接受被抑制边，源变更会明确 EXPIRE。
- `tests/test_oracle.py` 使用独立全点对可达性模型验证撤销 must 后仍有替代路径的情况，以及删除桥记录后才拆分；随机变化图同时检查约束撤销、替换及预算兜底。

这些测试证明实现遵守声明的治理语义，不证明任何特定真实公司判断正确。真实 10k 导入与发布验收不读取 truth_map，也不把模型预测伪装成人工已确认事实。
