# ADR 004：源记录、人工判断和统一身份分别建模

状态：按当前源码实现。记录日期：2026-09-12。

一个企业名称变化时，源记录可能仍是同一条登记记录；一个错误归并被纠正时，统一身份却可能发生拆分。若把源记录与企业 ID 合为一张可覆盖的映射，就无法同时解释这两类变化。因此系统分别保存源内稳定键与记录版本、判断事件、发布版本及企业成员。

`Store.import_records` 以 `(source_id, source_key)` 识别源记录，为新源记录生成 UUID。原始字段保存在追加的 `record_version.payload` 中；修改只切换 `source_record.current_version`，旧版本不覆盖。相同来源的相同逻辑批次内容可复用既有结果；部分更新中字段完全相同的记录也复用旧记录版本。`source_snapshot.content_sha256` 是排序后输入行的逻辑内容哈希，不冒充官方压缩包字节哈希；官方文件清单与实际下载哈希由数据接入产物保留。

`identity.assign_identities` 将成员分区映射为独立 UUID。成员集合完全相同就延续 ID，包括只更新记录字段而成员未变化的情况。成员增加、减少、合并或拆分时创建新 ID，再根据旧、新成员交集建立完整去向。多对多重组的一条 from/to 关系可以同时记录 SPLIT 与 MERGE，关系类型因此属于 lineage 主键。

记录全部消失的旧身份没有当前去向。旧 ID 当前查询先查已发布 lineage 的传递闭包，再返回所有仍有效的目标 ID；不会把拆分身份悄悄指向其中一个。指定历史 revision 则只读取该版本的成员与原字段，缺失该身份时返回未找到。数据库历史和产物都保留旧解释依据。

统一字段由 `Store.prepare_revision` 逐字段选择：Companies House 优先，其后按稳定源记录 UUID 排序，选第一个非空值。名称、地址、城市、邮编和国家都带 `source`、`record_version_id` 与选择规则。界面／API 仍能读各条源记录。这是可复现的展示策略，不是按多数票推断真值，也没有推断来源未提供的事实有效期。

企业身份源于 same-as 支持与显式约束。API 的 `relationships` 另存 branch_of/successor_of 的目标来源、源键和证据；这些字段本身不产生 union。可信登记号通道会排除带此类关系的记录。相似名称或共享地址也不是法律主体相同的证明；模型可能形成错误支持，需要独立 resolver 与人工纠错机制处理。

发布版本包含当时的记录、评分、约束、判断截止序号、企业成员、lineage、模型／策略及文件哈希。候选版不会从普通查询或固定版本导出暴露；发布检查通过后才切换当前指针。这里提供的是明确的版本历史，不是完整双时态数据库。

对应验收：`tests/test_identity.py` 验证 UUID 延续、合并／拆分去向、记录删除与无效分区；`tests/test_store.py` 验证重复导入、撤销后旧 ID 全部去向及历史读取；`scripts/check_real_workflow.py` 使用真实双源输入校验每个展示字段的值和来源版本确实属于该企业成员，并验证固定 revision 导出全覆盖。真实工作流不使用评测真值建立任何人工判断。
